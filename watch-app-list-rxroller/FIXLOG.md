# FIXLOG —— 本工程错误修复记录

> 本文件是**唯一**记录"踩过什么坑、怎么修的、怎么防止再犯"的地方。
> 源码里只留一行指路（`见 FIXLOG FX-###`），不写故事。
> 上游件改动另见 [`PORTLOG.md`](PORTLOG.md)；本文件只管**缺陷**。

条目格式：**现象**（看到什么，不带猜测）→ **复现**（一条命令/一个操作）→
**根因**（真正原因，含"为什么以前没发现"）→ **修复**（改了哪个文件什么）→
**证据**（可复跑的数字/输出）→ **防再犯**（门禁条目）。

分类：`U` = 上游缺陷；`M` = 我引入的回归；`T` = 取证/工具链坑；`G` = 假门禁。

## FX-001 · U · 拖动后列表自动回弹到松手那一行，滑不到底

- **现象**：慢慢拖到列表末尾松手，列表被动画切回松手时那一行，看起来像"回弹"；用户报"改的又问题，现在始终无法滑到底部"。
- **复现**：`run_sim.bat` 起窗口 → 从中间往下拖 → 中途停一下再松手。
- **根因**：上游 `rx_event_released` 用 `ctx->offset == 0` 判"是不是点击"，而 `offset` 是**单拍增量**（`touch_point1` 随即跟进）。松手前只要有一拍没动，`offset` 就是 0 ⇒ 整段拖动被判成点击，上游自己把列表动画切到那一行。
- **修复**：上游补丁 #2/#9/#10/#11 —— 新增 `ctx->drag_travel` 按拍累计位移，`is_click` 改判 `drag_travel <= RXROLLER_CLICK_TRAVEL_MAX(10px)`。账单见 PORTLOG §3。
- **证据**：`[WHEEL] click ignored: travel=…px` 不再出现于正常拖动；用户确认"现在可以了"。
- **防再犯**：`preflight` 第 4 组"产物 == 脚本重放结果"保证这四条补丁不会被手改丢掉。

## FX-002 · M · 我加的 60 ms 看门狗把列表锁在中间，滑不到底

- **现象**：修 FX-001 之前我曾加过一个每 60 ms 把中心夹回合法区间的定时器，结果列表彻底滑不动。
- **复现**：还原那次改动即可复现（用户直接回滚了）。
- **根因**：上游 `rx_event_released` 自己会在松手后做一次定位动画，我的定时器与它**抢方向盘**；夹回动作每 60 ms 打断一次上游动画。
- **修复**：删掉看门狗，改为事件触发的一次性纠正。
- **证据**：删除后拖动恢复；PORTLOG §4c 留了这条自纠记录。
- **防再犯**：经验库 `feedback-one-change-at-a-time`「轮询式纠正上游状态机 = 反模式」。

## FX-003 · U · 拖动被记成"在多行上按下"，位移算不出来

- **现象**：`row_click_cb` 里比"按下点 vs 松手点"永远算不出位移，拖动仍被当点击。
- **根因**：LVGL 在 `scroll_obj == NULL 且没有 PRESS_LOCK` 时**每个读周期重新搜索按下对象**（`lv_indev.c:1216-1219`），换对象时把 `last_point` 重置成当前点并给新对象再发一次 PRESSED ⇒ 按下点被中途刷新。
- **复现**：只加位移阈值不加 `PRESS_LOCK` 即可复现。
- **修复**：行加 `LV_OBJ_FLAG_PRESS_LOCK` 锁住手势目标 + 自己按拍累计位移兜底（两道一起上）。
- **证据**：`DRAG_CLICK_IGNORE_PX=15` 生效，轻点与拖动可区分。
- **防再犯**：注释只留一行指路；机制细节在本条。

## FX-004 · T · 22 行只画得出中心那一行

- **现象**：行的坐标全算对（abs y=9..492），屏上却只有中心一行。
- **根因**：上游把根对象留成 130×130 的"锚"，LVGL 9.4 子对象一律裁到父边界；`LV_OBJ_FLAG_OVERFLOW_VISIBLE` 只按 `ext_draw_size` 放宽（`lv_obj_pos.c:914`），**不取消裁剪**。
- **修复**：把根对象撑满宿主 + 用 `pad_left/pad_top` 保住原锚点坐标（不改上游坐标数学）。
- **证据**：`[WHEEL] anchor(140,186) kept, root=410x502`，5 行同屏。
- **防再犯**：`watch_list_dump("…")` 的 ancestor 链打印（`WATCH_ROWDEBUG=1`）会暴露谁在裁谁。

## FX-005 · T · 撑满宿主后 22 行全进绘制计算，快照卡死

- **现象**：`lv_snapshot_take` 在这棵树上 200 s 不返回，而同一棵树正常渲染是 210 拍/秒。
- **根因**：上游不做屏外回收；根撑满后 22 行全部进入绘制计算，快照路径放大成分钟级。
- **修复**：① 取证改读显示活动绘制缓冲 `lv_display_get_buf_active()`；② native 侧加 `CULL_PITCHES=4` 的隐藏回收。
- **证据**：`[SHOT] saved shot_*.bmp (410x502 stride=1640)` 秒级出图。
- **防再犯**：`preflight` 第 6 组要求 `LV_USE_SNAPSHOT` 与拍屏钩子在位；`take_shot()` 注释禁止再调 `lv_refr_now()`。

## FX-006 · U(误判) · 曾判定上游 `rx_calc_curve_pos` 漏初始化 `*x`

- **现象**：打完"`*x = 0`"补丁后卡死消失了，我据此认定上游有 bug 并写进 README。
- **根因（两层）**：① 上游原文 `Rxroller.c.orig:171-173` 开头就有 `*x = 0; *y = 0;`，判定是错的；② 卡死消失是**重试**生效（刚链接完立刻 exec 会瞬时 `rc=127`），与补丁无关。
- **修复**：撤销该补丁并重测，账单从 11 个 hunk 回到 10 个；PORTLOG §4 永久保留撤回记录。
- **证据**：`grep -n "\*x = 0" Rxroller.c.orig` 命中；撤销后断言照常 PASS。
- **防再犯**：经验库「判上游有 bug 前必须回读原文那几行」；"能解释现象的补丁 ≠ 正确的补丁"。

## FX-007 · U · 上游没有惯性（`inertia_divisor` 是死字段）

- **现象**：配置里写了 `inertia_divisor`，改它没有任何效果。
- **根因**：全文只有配置兜底那一处赋值（`if (… <= 0) … = 20;`），**再无第二处读取**；松手路径只 `rx_set_center_internal(best, 1)` 吸附到最近行。
- **修复**：惯性整套做在 native（测速 → `row_released_cb` → `watch_list_fling()`）。**上游账单未变。**
- **证据**：`[FLING] throw=-250px rows=-3 center=10 -> 13`。
- **防再犯**：`compare_upstream.py` 每次核账，能证明"加功能没顺手改上游"。
- **补充**：不能用 `rxroller_scroll(px)` —— 上游动画分支里 `offset` 只参与算时长（`Rxroller.c:725`），目标位置恒等于当前最近行。

## FX-008 · M · 圆角：`circularDisplay` 勾了没用，仿真还是方的

- **现象**：EEZ 画布里是圆的，仿真器四角笔直。
- **根因**：`settings.general.circularDisplay` / `displayBorderRadius` 在 EEZ Studio 的 `app.asar` 里 8 处命中**全在 React 预览渲染层**（给预览 DOM 加 CSS `border-radius`），代码生成器 0 处 ⇒ 纯编辑器装饰。另外 `displayBorderRadius=232` 是从 368×448 姊妹工程抄来的错值。
- **修复**：改走**控件级**属性：主屏 `radius=LV_RADIUS_CIRCLE(32767)` + `clip_corner=true`，全部由 EEZ 生成，native 零改动。
- **证据**：`src/ui/screens.c` 出现 `lv_obj_set_style_radius(obj, 32767, …)` 与 `lv_obj_set_style_clip_corner(obj, true, …)`；截图四角已裁圆。
- **防再犯**：`preflight` 第 1 组 3 条 —— radius/clip_corner 由 EEZ 生成、native 侧不许偷偷补。
- **附带事实**：410×502 上 `LV_RADIUS_CIRCLE` 出的是**胶囊**不是正圆（半径钳到 205，上下各 92px 直边，canvas 采样验证）。

## FX-009 · M · 加了圆角后标题和状态行被整个裁掉

- **现象**：`应用列表` / `就绪` 从截图上消失。
- **根因**：它们原本贴在直角上（`lbl_title` 在 (0,8)），胶囊一裁就裁没了。
- **修复**：外壳落点按弧算 —— 半宽 `h` 处需要的深度 `d = R - sqrt(R² - h²)`，取 `h=140` ⇒ `d≈56`；标签移到 (65,56) / (65,428)。
- **证据**：`OK lbl_title 落在胶囊安全区内 (65,56)`。
- **防再犯**：`preflight` 用同一条几何判据反查每个标签的左上/右上角；反向测试 `(60,56)` 会被拦、`(0,8)` 会被拦。

## FX-010 · M · 首尾磁吸：改上游钳位是"修过头"

- **现象**：第一行/最后一行能停在正中，没有"还有更多"的暗示。
- **第一版修复（错）**：把上游 `rx_clamp_distance` 的范围改成 `[CENTER_MIN, count-1-CENTER_MIN]`。断言全绿，但**把拖动行程一起锁死了** —— 与随后明确的口径"允许一路拖到最上/最下，松手才弹回"直接冲突。
- **根因（方法论）**：判据设计成了"我的兜底生效了"，而不是"绕过我的兜底还能过"。
- **修复**：整条上游补丁撤销（账单回到 14 个 hunk）；改为宏 `EDGE_SNAP_TOP_ORDINAL` / `EDGE_SNAP_BOTTOM_ORDINAL` + 松手一次性 `watch_list_snap_edge()`。
- **证据**：`首行可以拖到正中（行程不限）PASS 13 -> 0` 然后 `松手弹回顶部第 n 个 PASS 0 -> 1`；单变量把宏改 3 ⇒ 落点变"第 3 个"、区间变 `[2,20]`。
- **防再犯**：夹具必须**先断言行程放开**（绕开 native 的 `watch_list_center_no_clamp()`），再断言弹回。

## FX-011 · M · 真手滑到最上面不弹回，而 11 条无头断言全绿

- **现象**：用户上手反馈"我发先滑到最上面不返回了"，同一时刻 `WATCH_AUTOTEST` 11 条全 PASS。
- **根因**：手势回调只挂在**列表行**上；FX-005 的屏外回收把中心两侧 4 行以外的行置了 `HIDDEN`，而 LVGL 事件搜索跳过隐藏对象 ⇒ 手指按在"隐藏行/空白"上时按下目标是**滚轮根对象**，行回调一次都不触发，快滑与弹回**静默失效**。无头断言全部直接调行级 API，**绕过了整条 indev 链路**。
- **修复**：同一组回调（PRESSED/PRESSING/RELEASED/PRESS_LOST）也挂到滚轮根对象；两条路径最终归到同一个 `snap_edge_async`。
- **证据**：`WATCH_DRAGTEST=1` → `真拖动到顶：松手弹回顶部第 n 个 PASS`、`真拖动到底…PASS 中心=20`；标准 11 条无回归（合计 13/13）。
- **防再犯**：`preflight` 第 6 组 2 条 —— 手势回调必须同时挂行与根对象；必须存在走真 indev 的拖动夹具。反向测试：摘掉根上的 RELEASED 注册即 FAIL。

## FX-012 · T · 曾判定"SDL 事件注入到不了 LVGL 的 indev"（错的）

- **现象**：合成拖动收不到 PRESSED，我据此删掉了整套注入夹具，改请用户手滑一次。
- **根因**：上游 `lv_sdl_mouse.c:166-168` 的 `SDL_MOUSEBUTTONDOWN` 分支读的是 `event->motion.x / motion.y`（**不是** `button.x / button.y`）。按下事件不填 `motion` 字段 ⇒ 按下点落在 (0,0)，命不中任何控件。
- **修复**：`drag_send()` 里按下事件同时填 `motion.x/y`；夹具复活，FX-011 就是靠它复现的。
- **证据**：`[DRAG] 起始中心=1，往下拖 340px 松手` → 行/根回调正常触发。
- **防再犯**：夹具常驻 `WATCH_DRAGTEST`，preflight 检查其在位。

## FX-013 · T · 无头断言被真鼠标污染，量出不可复现的结果

- **现象**：夹定要判 `10 -> 13`，实际量成 `11 -> 15` ⇒ FAIL；重跑又可能过。
- **根因**：`WATCH_AUTOTEST` 并不挡住 SDL 真鼠标，窗口一开，一次手滑就改了中心行。
- **修复**：自证模式下 `lv_indev_delete(mouse)` 摘掉鼠标（`WATCH_ALLOWMOUSE=1` 恢复；`WATCH_DRAGTEST` 例外）。
- **证据**：连续两遍 5/5→13/13 稳定复现。
- **防再犯**：`preflight` 第 6 组检查摘除动作本身在位（"摘除"也是会被无声改回去的）。

## FX-014 · G · 假门禁：hunk 数用"字符串存在"判据

- **现象**：文档里第一处 `14 hunks` 改成 `99 hunks`，门禁仍然绿。
- **根因**：判据是 `"%d hunks" % n in text`，而文档里本来就有好几处。
- **修复**：改成**正则抓出文档里每一个 `<N> hunks`，要求每一处都等于实测值**；历史数字改用中文量词 `10 个 hunk` 不参与对账。
- **证据**：反向测试 `FAIL … 文档里出现了 [99]，实测是 14`。

## FX-015 · G · 假门禁：数 hunk 的口径与文档不一致

- **现象**：新门禁把正确的文档判成腐化（实测 19，文档 14）。
- **根因**：`difflib.unified_diff(n=0)` 会把相邻改动拆成更多块；`diff -u` 默认 `n=3` 合并成 14。
- **修复**：统一 `n=3`，与文档里写的 `diff -u` 同口径。
- **教训**：门禁自己用的工具，必须与它校验的那句话用的是**同一个口径**。

## FX-016 · G · 假门禁：字体覆盖比的是声明，不是产物

- **现象**：用户用 EEZ GUI 重新生成后，`ui_font_cn14.c` 被 EEZ 自己烘的版本（`--range` 配方）覆盖，而 preflight 第 3 组照报 OK。
- **根因**：该断言拿 native 用字比 `build_example.FONT_CHARS`（**声明值**），从没读过这份 `.c` 真正覆盖了哪些码点。
- **修复**：新增 `font_covered_codepoints()`，解析字体文件头部 lv_font_conv 回显的 `Opts:` 行取真实覆盖，再与用字、与声明做双向差集。
- **证据**：正向 `OK 实际字体文件覆盖 native 用字 54 个`、`OK 覆盖码点数(155) == 声明(155)`；反向（删 3 个码点）`FAIL 字体缺字 动天日`，而旧断言仍 OK。
- **顺带纠正**：P-0140 说"EEZ 不烘字体"只对 **CLI** 成立，**GUI 的 Build 会烘**。

## FX-017 · T · 改宏后单变量测试读到旧二进制

- **现象**：把 `EDGE_SNAP_TOP_ORDINAL` 从 2 改成 3，输出仍是"第 2 个"，差点结论成"宏没生效"。
- **根因**：ccache + mtime 让 ninja 判定 obj 是新的，**只重链不重编**。
- **修复**：测前 `touch` 源文件，并确认构建日志里有 `Building … .obj` 那一行（只有 `Linking` 就是没重编）。
- **教训**：任何"改一个常量看行为跟不跟"的裁决实验，先证明二进制真的换了。

## FX-018 · T · 上游原文哈希"对不上"其实是行尾

- **现象**：`.orig` 与上游克隆的 `Rxroller.c` SHA256 不同，看着像被人改过。
- **根因**：入库时归一化成 LF，上游仓库是 CRLF；差的 1204 字节正好等于行数。
- **修复**：`compare_upstream.py` 归一化行尾后再比，并做**整仓对账**（上游每个文件必须有归属）。
- **证据**：`OK Rxroller.c 上游 3a364084ef49 vs 入库 Rxroller.c.orig 逐字节一致（归一化行尾后）`。

## FX-019 · T · heredoc 改 C 源码掉一层转义（本轮第 5 次）

- **现象**：用 bash heredoc / python 内联脚本往 .c 里插 `printf("...\n")`，编译报 `missing terminating " character`；探针一条没打，差点误判成"回调没触发是因为代码没跑"。
- **根因**：`\n` 经 heredoc 传进去变成真实换行。
- **修复**：含转义的源码片段一律用编辑器工具改；临时规避写法 `printf("...%c", 10)`。
- **防再犯**：已进经验库；本轮再次违反并再次踩中，记录在此作为代价证明。

## FX-020 · M · 把"中心图标放大"听成"把所有图标做大"

- **现象**：用户说"中心的图标要求放大"。我把 `ICON_PX` 76→96、行距 100→112 一起放大了。
- **根因**：没分清"放大"指的是**缩放曲线的对比度**（选中 vs 未选中），还是位图本身。
  用户澄清："放大不是所有放大，而是没有选中最小，当选中时候最大，中间的比例线性分档。"
- **修复**：`ICON_PX` 回到 76、`ROW_PITCH` 回到 100；真正要调的是
  `SCALE_SPAN_PITCHES`（分几档）与 `SCALE_EDGE_PCT`（最小档多小）。
- **教训**：观感动词先问"跟谁比、比什么量"，再决定改哪个参数。本轮已经靠
  `AskUserQuestion` 给数值选项才收敛 —— 第一轮就该给。

## FX-021 · G · 断言写死了上一轮参数的**形状**，参数一改就假 FAIL

- **现象**：把 `SCALE_SPAN_PITCHES` 从 1 改成 3 之后，三条断言同时 FAIL
  （"1 行以外全是最小档""紧邻行已是最小档""缩放随距离线性过渡"），
  而产品行为其实完全正确 —— 剖面 `150 185 220 255 220 185 150` 正是新口径要的。
- **根因**：那三条把"span=1"这个**具体形状**写进了判据（`c0 <= EDGE+2`、
  `255 - (255-EDGE)*|d|/pitch`），等于把参数抄了一遍到夹具里。参数是配置项，
  配置项变了，抄下来的判据必然过期。
- **修复**：判据改成**从 config 反推公式**：夹具 include `watch_list_config.h`，
  用 `SCALE_AT(d)` / `SCALE_CONT(d)` 按 `SPAN`/`EDGE_SCALE` 算期望值，
  断言名也从"紧邻行…"改成"缩放按 SPAN 线性分档""离中心 SPAN 行处到底"。
- **证据**：改完 16/16 PASS；且把 `SPAN` 改成 1/2/4 都不需要再动断言。
- **防再犯**：`preflight` 第 6 组按名字核对 16 条断言在位，并提示
  "断言名要按 config 验通用公式，不许写死形状"。
