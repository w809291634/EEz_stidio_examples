# Flow 执行语义（P6.2 / P6.3 · 手册 P.40–P.42）

> 这一篇是**理解 Flow 的地基**：仓库里几个反复踩的坑（Checks 空转、"画了不连"、
> 第二次触发不生效、SetVariable 后没反应）本质都是这里的规则。
> 锚点：`MANUAL_MAP.md` → P6.2 = raw 行 1889（P.40）、P6.3 = raw 行 1959（P.42）。

## 1. 五种基本元素（P6.1 · P.39）

| 元素 | 手册定义要点 |
|---|---|
| Widget | 页面上可见的图形件；**可以和 Action 混用**，可定义输入/输出（左右半圆） |
| User Widget | 把含图形件的一段流程打包复用，靠 Input/Output Action 与外界相连 |
| Action | 页面上**不可见**，至少有一个输入或输出 |
| User Action | 把一段逻辑打包复用，用 **Start / End / Input / Output** 作连接点 |
| Sequence line | 只传"执行时机"，不传数据（手册原话：收到的是 "null data"）；未选中时**青绿色** |
| Data line | 既传执行时机**又传数据**（integer / string / structure…）；未选中时**灰色** |

★ 颜色的工程意义：在 EEZ 编辑器里**看线色就能判断这条线是时序还是数据**，
排查"数据没过去"时先确认线型，而不是先怀疑表达式。

## 2. 就绪判定（P6.2 · 全篇最关键的一条）

手册原文规则（**逐条照抄，别脑补**）：

1. 全局只有一条**执行队列**（execution queue），**所有活跃 Flow 共用**——这就是 `executionQueueSize`
   占静态 SRAM 的原因（P13.2 · P.100，本仓库实测 1000→128 省 10,464 B RAM，见经验库 P-0157）。
2. 一个件收到数据线送来的数据时，它被**排到队列尾部**；但只有当它
   **所有数据输入都有数据** 且 **至少一个时序输入收到过**（若它存在时序输入）时才"就绪可执行"。
3. **没有连线终接的输入，不参与上面的判定**（手册："if there is no Flow line that ends in an input, then that input is not looked at in this test"）。
4. 只要**某一个**时序输入收到数据即可（Loop 有 Start / Next 两个时序输入，任一个到达都算）。
5. **执行结束时**：所有**时序输入的数值被清除**，**数据输入保留最后一次的数值**。
   → 推论：之后只要再来一条时序线，这个件会**用旧数据再执行一次**，
     除非某个件自己声明会清除某个数据输入（手册说这类件会在其描述里专门写明）。
6. **完全没有输入（或没有任何线终接）的件**：Flow 启动时**立即入队执行** —— `Start` 就属于此类。
7. 两个**例外**（无输入但不立即执行）：`CatchError`（只在出错时执行）、`OnEvent`（只在页面事件发生时执行）。
8. **Widget 也是执行参与者**：它可以在输入上收值、在输出上送值；Widget 被"立即执行"。
9. 带内部状态的件（`Loop`、`Delay`、`SCPI`…）做完一部分工作会**把自己重新排队**，
   手册的说法是"这样实现了所有 Flow 的并行执行，即不必等 SCPI 跑完所有命令，别的件才能执行"
   —— 队列交替推进，**不是抢占式多线程**（Debugger 里这类件有特殊图标）。

### 用这套规则解释仓库里的老坑

| 老坑 | 规则解释 |
|---|---|
| P-0146 Switch/Checks 面板死循环、 Checks 空转 | 第 2 条：Switch 的数据输入（`evt`）没有数据 → 永不就绪；本仓库解法是给 `evt` 声明 `type:'any'` |
| "画了不连"报 not connected | 第 3 条：无连线终接的输入不参与判定，但**有连线却没送数据**就是卡住；单向手势示例因此选择**干脆不生成另一方向的件** |
| 第二次点击没反应 / 状态残留 | 第 5 条：数据输入保留旧值、时序输入被清除——想"每次带新值"必须由数据线重新送，不能指望时序线触发时数据自动刷新 |
| `Watch` 启动就发一次值 | 第 6/9 类件行为 + P8.1 明说："At Flow start, it always sends the current value via the Changed data flow line"（**不是坑，是设计**） |

## 3. 四个连线反例（P6.3 · P.42，手册 Fig.58/59）

| Case | 连法 | 结果（手册结论） |
|---|---|---|
| #1 | User Action 内有 `Start` ⇒ 时序输入**必需**；再串 `Delay(1s)` | 1 秒后显示字符串 |
| #2 | 时序输入必需，但**什么都没接** | **不执行**；编辑器报错 |
| #3 | 用 `action_without_start`（时序输入非必需） | 与 #1 同结果 |
| #4 | 时序输入非必需 + `Constant` 直接送数据 | **启动即执行**（无延时） |

★ 手册原话要点：**"虽然 case #2 在编辑器里报错，但这样的 Flow 仍允许运行"**
——目的是"还没连完也想先测已做的部分"。
所以：**编辑器报错 ≠ 不能构建；构建成功 ≠ 逻辑会跑**。本仓库的判据因此必须是
"日志标记 + 产物对账 + 行为验收"三件齐全（P-0005），不能只看构建绿。

## 4. 观测面（GUI 才有，别指望 headless）

Debug 模式提供三个面板（P6.2 · Fig.56/57）：

- **Active Flows**：当前活跃 Flow（数字是它状态的**内存地址**，如 1184）；跑完的从队列消失；
- **Watch**：全局变量 + 当前活跃 Flow 的**局部变量** + **下一个待执行件的输入状态**；
- **Queue**：逐条看清哪个输出把值发给了哪个输入（例如 `Start 输出 → Loop 的 Start 输入`）。

→ **方法结论**：Flow "不刷新"这类问题的第一手证据在 Queue/Watch 面板里，
而不是在生成的 C 代码里。headless CLI 拿不到这两块，必须开 EEZ Studio GUI 的 Debug。
这条决定了下面示例规划里"观测类"示例必须标注 **GUI-only**（PC_SIM 只验行为，不验队列）。
